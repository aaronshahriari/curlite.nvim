==============================================================================
1. INTRODUCTION                                         *curlite-introduction*

curlite runs HTTP requests written in `.http` files — the same format that
JetBrains IDEs, VS Code's REST Client and kulala.nvim use — and shows the
response in a split.

Requests go out through `curl`. Nothing else is needed: no language server, no
companion binary, no Node. What arrives comes back out of band (headers to one
file, body to another, timings as JSON on stdout), so a body that happens to
contain header-looking lines can't confuse the parser and a large download
never passes through Lua twice.

Pre- and post-request scripts are written in **Lua**, not JavaScript. You are
already in a Lua editor; the interpreter is free and the sandbox is one table.

==============================================================================
2. REQUIREMENTS                                         *curlite-requirements*

    Neovim 0.10+
    curl                (7.75+ for the Stats pane; older still works)

Optional:

    jq                  the `gq` filter in the response window. Formatting
                        does not need it
    blink.cmp           completion inside `.http` files
                        (|curlite-completion|)
    a treesitter `http` parser
                        used for highlighting if present; curlite ships a
                        syntax file that is used otherwise
    lualine.nvim        the statusline component (|curlite-statusline|)

Run `:checkhealth curlite` to see what is available.

==============================================================================
3. INSTALLATION                                         *curlite-installation*

With |vim.pack| (Neovim 0.12+): >lua

    vim.pack.add({
      { src = "https://github.com/aaronshahriari/curlite.nvim" },
    })
    require("curlite").setup({})
<
With lazy.nvim: >lua

    {
      "aaronshahriari/curlite.nvim",
      ft = { "http" },
      cmd = { "Curlite", "CurliteRun" },
      opts = {},
    }
<
`setup()` must run for curlite to register its filetypes, keymaps and
commands. Calling it more than once is safe.

`.http` is detected by Neovim itself. curlite additionally maps `.rest` and
`*.http.*` (so `api.http.dev` works) onto the `http` filetype; set
`filetype.register = false` if you would rather own that yourself.

==============================================================================
4. QUICK START                                           *curlite-quick-start*

Put this in `api.http`: >

    @host = https://httpbin.org

    ### GET_IP
    GET {{host}}/ip
    Accept: application/json
<
Park the cursor anywhere in it and press `<leader>Rs`. The response opens in a
split on the right, with the status and timing in the winbar, and
`  200 OK` appears at the end of the request line. Timing, size and test totals
can be enabled there with `ui.inline`.

`L` and `H` move between panes: the body, the response headers, both together,
timing and size statistics, curl's verbose trace, and anything your scripts
logged.

Then add an environment file next to it, `http-client.env.json`: >

    {
      "$curliteshared": { "apiVersion": "v1" },
      "dev":  { "host": "http://localhost:3000" },
      "prod": { "host": "https://api.example.com" }
    }
<
Drop the `@host` line, press `<leader>Re` to pick an environment, and the same
request now runs against either one.

Nothing is selected until you pick: opening a `.http` file always starts with
no environment, and the first send opens the picker instead of going out
against whichever one you used last. See |curlite-environments|.

==============================================================================
5. THE .HTTP FORMAT                                           *curlite-format*

------------------------------------------------------------------------------
REQUESTS                                             *curlite-format-requests*

A line of three or more `#` separates requests. Anything after it is the
request's name: >

    ### Fetch the current user
    GET https://api.example.com/me

    ### Create one
    POST https://api.example.com/users
<
`# @name` does the same thing and wins if both are present. Names matter: they
are how |curlite-request-variables| and |curlite-chaining| refer to a request.

Add `[confirm]` anywhere in the separator title to guard a request that should
not run accidentally. The marker is removed from the request name: >

    ### [confirm] Delete production user
    DELETE {{prod}}/users/42
<
Before sending, curlite shows the fully resolved request in a centered popup.
Choose `y` or `n`, then press Enter. Declining skips the request without
stopping a "send all" run. `# @confirm` provides the same behavior.

Every resolved-request preview -- this popup, |curlite-inspect| and
|curlite-hover| -- indents a JSON body for display, so a payload written on one
line is still readable. `format.bodies = false` turns that off along with the
buffer formatter.

The method is optional — a bare URL is a GET. A trailing `HTTP/1.1` is
recognised and forces that protocol version.

A file with no `###` separators still works: a line at column 0 that starts
with a method and follows a blank line begins a new request. (A URL containing
a space is never treated as a request line, which is what keeps this from
firing on prose inside a body.)

A long query string can be split across lines. A line indented by at least one
space and beginning with `?`, `&` or `#` is appended to the URL: >

    GET https://api.example.com/search
      ?q=neovim
      &lang=lua
      &limit=25
<
------------------------------------------------------------------------------
HEADERS AND BODIES                                       *curlite-format-body*

Headers follow the request line, one per line, until a blank line. A
continuation line (indented) is folded onto the header above it. `Name:` with
no value sends an empty header rather than dropping it.

Everything after the first blank line is the body, verbatim. Two cases are
handled specially:

  * `application/x-www-form-urlencoded` bodies have their newlines removed.
    This is how these are written in practice — >

        POST https://api.example.com/token
        Content-Type: application/x-www-form-urlencoded

        grant_type=client_credentials
        &client_id={{clientId}}
        &scope=read write
<
    and the newlines are formatting, not data. Every REST client strips them;
    sending them literally is always a 400.

  * a body that parses as JSON and has no `Content-Type` gets
    `application/json`. Set `request.infer_content_type = false` to stop that.

A missing blank line between the headers and the body is forgiven: the first
line that isn't a header starts the body.

------------------------------------------------------------------------------
METADATA                                                    *curlite-metadata*

A comment of the form `# @key value` (or `// @key value`) configures the
request it precedes. Ordinary comments are ignored.

Metadata is normally written above the request line, but the `@key` form is
also recognised inside a body, so `# @assert` after a script block works. A
plain `#` comment inside a body stays part of the body, so a Markdown heading
or a YAML comment in a payload survives.

                                                       *curlite-metadata-list*
    @name NAME          name this request
    @prompt NAME DESC   ask for a value before sending (|curlite-prompts|)
    @assert EXPR        check the response (|curlite-assertions|)
    @run NAME           send another request first (|curlite-chaining|)
    @import PATH        make another file's requests available
    @accept TYPE        shorthand for the Accept header
    @timeout MS         abandon the request after this long
    @delay MS           wait this long before sending
    @insecure           skip TLS certificate verification
    @no-redirect        do not follow redirects
    @max-redirs N       follow at most N redirects
    @compressed         request and decode a compressed response
    @http2 @http3 @http1.1
                        force a protocol version
    @proxy URL          send through a proxy
    @unix-socket PATH   connect over a unix socket
    @cert PATH          client certificate
    @key PATH           client key
    @cacert PATH        CA bundle
    @resolve H:P:ADDR   pin a hostname to an address
    @interface NAME     bind to a network interface
    @retry N            retry a transient failure N times
    @user USER:PASS     credentials, passed to curl's --user
    @graphql            treat the body as a GraphQL query
    @confirm            show the request and require confirmation before send
    @skip               never send this request; a "send all" steps over it
    @no-cookie-jar      don't read or write the shared cookie jar
    @curl ARGS          raw curl flags, appended verbatim

`@curl` is the escape hatch. Anything curl can do that curlite hasn't given a
name to: >

    # @curl --tlsv1.3 --limit-rate 200k
    GET https://api.example.com/large
<
------------------------------------------------------------------------------
MULTIPART                                                  *curlite-multipart*

Write the body with explicit boundaries and curlite converts it to curl `-F`
arguments (letting curl generate the real boundary): >

    POST https://api.example.com/upload
    Content-Type: multipart/form-data; boundary=CurliteBoundary

    --CurliteBoundary
    Content-Disposition: form-data; name="title"

    Holiday photo
    --CurliteBoundary
    Content-Disposition: form-data; name="photo"; filename="beach.jpg"
    Content-Type: image/jpeg

    < ./beach.jpg
    --CurliteBoundary--
<
A part whose content is `< ./path` sends that file; anything else is sent
literally.

------------------------------------------------------------------------------
GRAPHQL                                                      *curlite-graphql*

Use the `GRAPHQL` method, an `X-REQUEST-TYPE: GraphQL` header, or
`# @graphql`. The body is the query; a blank line followed by a JSON object
supplies the variables: >

    GRAPHQL https://api.example.com/graphql

    query User($id: ID!) {
      user(id: $id) { name email }
    }

    { "id": "42" }
<
curlite sends `{"query": "...", "variables": {...}}` as JSON.

------------------------------------------------------------------------------
FILES IN AND OUT                                               *curlite-files*

    < ./payload.json    send this file as the body. curl streams it, so the
                        size doesn't matter.
    >> ./out.json       write the response body here, refusing if the file
                        exists
    >>! ./out.json      write it, overwriting

Relative paths are relative to the `.http` file, not your working directory.

==============================================================================
6. VARIABLES                                               *curlite-variables*

`{{name}}` anywhere in a URL, header name, header value, body or `@curl`
argument is substituted before the request goes out. Resolution is recursive,
so `@base = {{host}}/v1` works.

When a name can't be resolved the request is refused rather than sent with a
literal `{{name}}` in it, and the error says which names were missing.

Lookup order, first hit wins:

    1. dynamic functions    {{$uuid}}, {{$env.FOO}}, ...
    2. request variables    {{LOGIN.response.body.$.token}}
    3. script globals       client.global.set("x", ...)
    4. prompt answers       # @prompt
    5. document variables   @token = abc
    6. environment          http-client.env.json

------------------------------------------------------------------------------
DOCUMENT VARIABLES                                *curlite-variables-document*

A line beginning with `@` at column 0: >

    @host = https://api.example.com
    @token = {{$env.API_TOKEN}}
<
By default a variable is visible to the requests *below* it, so redefining one
mid-file does what it looks like. Set `request.variables_scope = "document"`
for kulala's behaviour, where every request in the file sees every variable
regardless of order.

------------------------------------------------------------------------------
ENVIRONMENTS                                            *curlite-environments*

`http-client.env.json` beside your `.http` file — or in any directory above
it — defines one object per environment: >

    {
      "$curliteshared": { "apiVersion": "v1" },
      "dev":  { "host": "http://localhost:3000" },
      "prod": { "host": "https://api.example.com", "auth": {
                  "clientId": "abc" } }
    }
<
`$curliteshared` is merged under every environment. JetBrains' `$shared` is
read as well, so a file written for another client works here unchanged; when
a file carries both, `$curliteshared` wins where they define the same key.
`env.shared_key` sets which names are looked for.

Nested objects are reachable with a dotted name: `{{auth.clientId}}`.

`http-client.private.env.json` is merged over the public file and is the one
to gitignore. Files nearer the `.http` file win over ones further up, so a
sub-directory can override a project-wide default.

`//` and `/* */` comments in these files are tolerated (a `//` inside a
string, as in `https://`, is left alone).

DEFAULT HEADERS                                         *curlite-env-headers*

A `$default_headers` object holds headers sent with every request in the
project. It sits beside the variables, in a shared key or in an environment
or both: >json

    {
      "$shared": {
        "$default_headers": {
          "Accept": "application/json",
          "X-Client": "curlite"
        }
      },
      "dev": {
        "host": "http://localhost:3000",
        "token": "dev-token"
      },
      "prod": {
        "host": "https://api.example.com",
        "token": "{{$dotenv PROD_TOKEN}}",
        "$default_headers": {
          "Authorization": "Bearer {{token}}",
          "X-Client": false
        }
      }
    }
<
This is where a header that belongs to a *project* goes, as opposed to one
that belongs to your editor (`request.default_headers`, in your Lua config) or
to a single request (the header line itself). Three things follow from that:

    - `{{...}}` in a value is substituted against the request that is going
      out, so `"Bearer {{token}}"` picks up whichever token the selected
      environment defines. `$dotenv`, `$uuid`, globals set by a script and
      the rest of |curlite-variables| all work.

    - An environment's headers are merged over the shared ones, so `prod`
      above sends `Accept` from `$shared` and `Authorization` of its own. A
      value of `false` drops an inherited header instead of sending it —
      `prod` sends no `X-Client` at all.

    - A request that sets the header itself always wins, whatever the case
      it writes it in. Nothing is sent twice.

In full, later wins: >

    request.default_headers  (your Lua config)
        <  $default_headers in a shared key
        <  $default_headers in the selected environment
        <  the header on the request itself
<
The resolved headers are what `:Curlite inspect`, `hover` and `curl` show, so
a request's real shape is always one keystroke away. The picker lists them
under the variables, and `:checkhealth curlite` names the ones currently in
force.

These keys are not variables: `{{$default_headers}}` resolves to nothing and
they never appear in completion or the picker's variable block.
`env.headers_key` sets which names are looked for.

SELECTING ONE                                         *curlite-env-selecting*

An environment is active because you chose it, and for no other reason.
curlite never selects the first one it finds, and never carries a choice over
from another file or another day: opening a `.http` file starts with none.

With none selected and environments defined, sending stops and opens the
picker; the request goes out once you have chosen. Set
`env.require_selection = false` to let requests run against the shared
variables alone instead, or `env.default = "dev"` to have one active from the
start without being asked.

Pick with `<leader>Re` or `:Curlite env`. The picker shows the environments on
the left and, on the right, the variables the highlighted one resolves to —
the shared block merged with its own values, pretty-printed, each top-level
key marked with where it came from, and under them the headers it adds to
every request (|curlite-env-headers|). The preview is rebuilt for whichever
entry is highlighted, so it is a live view of the file rather than a snapshot.
That is the point of it: you choose by reading the host you are about to send
to rather than by remembering which name meant which stack.

                                                        *curlite-env-telescope*
With telescope.nvim installed that is a telescope picker, so the list is
fuzzy-findable and follows whatever layout and theme you have set for
everything else; without it, curlite opens a window of its own. Either way the
list, the preview and the proportions are the same, and curlite depends on no
plugin. `ui.picker.backend` decides: >lua

    ui = {
      picker = {
        backend = "auto",       -- telescope when installed, else built-in
        -- backend = "builtin", -- always curlite's own window
        -- backend = "telescope",
        telescope = {           -- passed to telescope's picker
          layout_strategy = "vertical",
        },
      },
    }
<
`:checkhealth curlite` says which one you are getting.

There is a telescope extension too, for driving it from `:Telescope`: >lua

    require("telescope").load_extension("curlite")
<
    :Telescope curlite                  the environment picker
    :Telescope curlite theme=dropdown   with a theme

Keys in the built-in picker:

    <CR>          take the highlighted environment
    j k           move, previewing as you go
    q  <Esc>      leave the selection as it was

The telescope one uses your telescope mappings.

The first entry, `(no environment)`, previews the shared block alone and
selects nothing. Choosing it counts as having chosen, so sends stop asking.

The choice lives for this Neovim session, keyed on the nearest directory
holding an env file or a `.git`, and is dropped when a `.http` file in that
project is opened again.

The scripted entry points — |curlite.inline()|, |curlite.inline_sync()| and
|curlite.run_file()| — are never gated this way: they run what you handed
them, against whatever is selected.

A `.env` file in the same directories is read too, and is reachable as
`{{$dotenv NAME}}`.

------------------------------------------------------------------------------
DYNAMIC VARIABLES                                            *curlite-dynamic*

    {{$uuid}}                   a random v4 UUID ({{$guid}} is the same)
    {{$timestamp}}              seconds since the epoch
    {{$timestamp -1 d}}         shifted; units ms s m h d w M y
    {{$isoTimestamp}}           2026-09-27T12:00:00Z
    {{$isoTimestamp 7 d}}       shifted
    {{$datetime iso8601}}       also rfc1123, unix, or a strftime format
    {{$datetime "%Y/%m/%d" -1 d}}
    {{$localDatetime iso8601}}  the same, in local time
    {{$date}}                   today; {{$date %d/%m/%Y}} to choose a format
    {{$time}}                   now
    {{$randomInt 1 100}}        an integer in a range
    {{$randomAlphaNumeric 16}}  a random string
    {{$randomHex 16}}
    {{$randomEmail}}
    {{$randomFirstName}} {{$randomLastName}} {{$randomFullName}}
    {{$env.NAME}}               a process environment variable
    {{$env NAME}}               the same
    {{$processEnv NAME}}        the same
    {{$dotenv NAME}}            from the nearest .env file
    {{$exec COMMAND}}           stdout of a shell command, trailing newline
                                stripped. Evaluated once per run -- a "send
                                all" over thirty requests shells out once,
                                not thirty times -- and re-read on the next
                                send. A non-zero exit is reported rather
                                than substituted.

IntelliJ's spellings also work: `{{$random.integer(1, 100)}}`,
`{{$random.uuid}}`, `{{$random.alphanumeric(8)}}`, `{{$random.float(0, 1)}}`,
`{{$random.hexadecimal(12)}}`, `{{$random.email}}`.

`{{$exec}}` is how to reach a secret manager without putting it in a file: >

    @token = {{$exec pass show api/example/token}}
<
------------------------------------------------------------------------------
REQUEST VARIABLES                                  *curlite-request-variables*

Once a named request has run, later requests can read its response: >

    ### LOGIN
    POST https://api.example.com/login

    { "user": "aaron", "password": "{{password}}" }

    ### ME
    GET https://api.example.com/me
    Authorization: Bearer {{LOGIN.response.body.$.data.token}}
<
    NAME.response.body.$.a.b[0].c   a JSONPath into the body
    NAME.response.body              the whole body as text
    NAME.response.headers.NAME      a response header (case-insensitive)
    NAME.response.status            the status code
    NAME.response.cookies.NAME      a cookie the response set
    NAME.request.body.$.x           what was sent
    NAME.request.headers.NAME

Array indices are 0-based, as JSONPath expects. `$last` refers to whatever ran
most recently.

These live for the session. If the referenced request hasn't run yet the
request is refused with a clear message — or use `# @run` to have curlite run
it for you (|curlite-chaining|).

------------------------------------------------------------------------------
PROMPTS                                                      *curlite-prompts*

>
    # @prompt token Paste your bearer token
    # @prompt env_name Which tenant?
    GET https://api.example.com/me
    Authorization: Bearer {{token}}
<
Asked once per session and then reused. `:Curlite clear` forgets the answers.

==============================================================================
7. AUTHENTICATION                                               *curlite-auth*

Most schemes are written as an ordinary `Authorization` header and mapped onto
the curl flag that implements them — which matters for Digest and NTLM, where
the challenge needs two round trips that curl handles itself.

    Authorization: Bearer {{token}}
                        sent as-is
    Authorization: Basic alice s3cret
    Authorization: Basic alice:s3cret
                        base64-encoded for you. A value that is already
                        base64 is passed through untouched.
    Authorization: Digest alice s3cret
    Authorization: NTLM alice s3cret
    Authorization: Negotiate
    Authorization: AWS KEY SECRET [region] [service]
                        AWS SigV4; region defaults to us-east-1 and service
                        to execute-api

Client certificates use `# @cert`, `# @key` and `# @cacert`.

There is no built-in OAuth2 flow. For client credentials, write the token
request as a request and chain it: >

    ### TOKEN
    POST {{host}}/oauth/token
    Content-Type: application/x-www-form-urlencoded

    grant_type=client_credentials
    &client_id={{clientId}}
    &client_secret={{clientSecret}}

    > {% client.global.set("access_token", response.json.access_token) %}

    ### ANYTHING
    # @run TOKEN
    GET {{host}}/v1/things
    Authorization: Bearer {{access_token}}
<
For a browser-redirect flow, get the token however you normally would and
reach it with `{{$exec}}`.

Cookies are kept in a shared jar (`curl.cookie_jar`), so a login request's
session carries into the next request without you doing anything.

==============================================================================
8. SCRIPTS                                                   *curlite-scripts*

A `< {% ... %}` block runs before the request, a `> {% ... %}` block after it.
`< ./file.lua` and `> ./file.lua` run a script from disk. The language is Lua.

>
    ### LOGIN
    < {%
      request.headers.set("X-Request-Id", client.global.get("run_id"))
    %}
    POST https://api.example.com/login

    { "user": "aaron" }

    > {%
      client.global.set("token", response.json.data.token)
      client.log("token expires in " .. response.json.data.expires_in)

      client.test("got a token", function()
        assert(#response.json.data.token > 20, "token looks too short")
      end)
    %}
<
Everything `client.log` prints and every `client.test` result appears in the
response window's Script pane.

                                                      *curlite-script-request*
`request` (both phases, mutable) ~

    .method .url .body           assign to them to change what is sent
    .headers.get(name)           case-insensitive
    .headers.set(name, value)
    .headers.remove(name)
    .headers.all()
    .variables.set(name, value)  a document variable, this request only
    .variables.get(name)
    .metadata                    the request's `# @` metadata
    .skip([reason])              don't send this request
    .abort([reason])             stop a "send all" run here

                                                     *curlite-script-response*
`response` (post-request only) ~

    .status .status_text .http_version
    .body                        the raw body
    .json                        decoded, or nil
    .headers                     case-insensitive lookup
    .header(name)
    .cookies
    .duration_ms
    .stats                       everything in the Stats pane

                                                       *curlite-script-client*
`client` (both phases) ~

    .global.set(name, value)     visible as {{name}} from here on, for the
                                 rest of the session
    .global.get(name)
    .global.clear([name])
    .global.all()
    .log(...)                    to the Script pane
    .test(name, fn)              a named assertion block
    .assert(cond, message)
    .exit()                      stop this script

Also in scope: `json` (|vim.json|), `env` (a read-only copy of the active
environment), `log` and `print` (both aliases for `client.log`), and the pure
parts of the standard library. `io`, `os.execute`, `debug`, `jit` and the
loaders are not, with `scripts.sandbox = true`; set it to `false` if you
script against your own modules.

==============================================================================
9. ASSERTIONS                                             *curlite-assertions*

`# @assert` takes a Lua expression evaluated against the response: >

    # @assert status == 200
    # @assert json.data.id ~= nil
    # @assert #json.items == 25
    # @assert headers["content-type"]:find("json")
    # @assert duration < 1000
    GET https://api.example.com/items
<
In scope: `status`, `body`, `json`, `headers` (lower-cased keys), `cookies`,
`duration` (milliseconds), and `response`.

Results appear in the Script pane and as a `3/4` tally in the winbar and on
the request line. `client.test()` in a post-request script is the same
mechanism with room for several statements.

`:CurliteRun path/to/file.http` runs a whole file and reports the totals,
which is the closest thing to a test runner here.

==============================================================================
10. CHAINING REQUESTS                                       *curlite-chaining*

`# @run NAME` sends another request first: >

    ### REFRESH
    POST {{host}}/auth/refresh
    Content-Type: application/x-www-form-urlencoded

    refresh_token={{refresh_token}}

    > {% client.global.set("token", response.json.access_token) %}

    ### ORDERS
    # @run REFRESH
    GET {{host}}/orders
    Authorization: Bearer {{token}}
<
Several `# @run` lines run in the order written. A dependency's own `# @run`
is followed too. A cycle terminates: a request already in the chain is not run
again. If a dependency fails or aborts, the request that needed it is not
sent.

`# @import ./auth.http` makes another file's named requests available to
`# @run` and to |curlite-request-variables|. Imports are followed up to five
levels deep, a file already seen is skipped, and the importing file wins on a
name clash — so a local override behaves as expected.

==============================================================================
11. THE RESPONSE WINDOW                              *curlite-response-window*

One window, six panes. The pane list sits in the winbar on the right and is
clickable; the status, timing, size and assertion tally sit on the left:

    ` 201 Created  140ms  1.2KB  3/4    Body Headers All Stats Verbose Script`

------------------------------------------------------------------------------
THE PANES                                                      *curlite-panes*

                                                          *curlite-pane-body*
Body ~
    The response body, formatted, and nothing else. No status line, no
    headers, no banner. That matters: because the buffer holds only the body,
    it gets a real `filetype` (json, xml, html, ...) so treesitter highlights
    it properly, `gq` filters it through `jq`, and `Y` yanks exactly what
    the server sent.

    JSON is pretty-printed in pure Lua, without spawning anything. The
    formatter walks the source text rather than decoding and re-encoding, so
    key order is preserved and a 64-bit id does not round-trip through a
    double and come back as `1.2345678901235e+19`. (`jq` was used here once
    and measured slower at every body size: a process spawn costs more than
    formatting anything under a megabyte.)

    A binary body (by Content-Type, or a NUL in the first kilobyte) is
    described rather than dumped into the buffer. Press `gs` to save it.

                                                       *curlite-pane-headers*
Headers ~
    The response headers, sorted. Every redirect hop is shown in order, each
    with its own status line, so a 301 → 302 → 200 chain is visible at a
    glance. Repeated headers (`Set-Cookie`, `Link`) are joined rather than
    lost.

                                                           *curlite-pane-all*
All ~
    The request as it was actually sent — method, URL, headers and body,
    after variable substitution — then a divider, then the response headers
    and body. This is the pane for "what did I actually send?". Set
    `response.show_request = false` to drop the request half.

                                                         *curlite-pane-stats*
Stats ~
    Where the time went and how big everything was, from curl's own
    instrumentation rather than anything curlite measured:

        Response      status, HTTP version, method, content type, effective
                      URL, redirect count
        Timing        DNS lookup, TCP connect, TLS handshake, request sent,
                      waiting (TTFB), download, total
        Size          response body, response headers, request sent, request
                      body, download speed
        Connection    remote address and port, local port, connections
                      opened, TLS verification result
        Cookies set   anything the response set

    The timing rows are deltas, not cumulative offsets: "TLS handshake" is
    the handshake alone, not everything up to the end of it.

                                                       *curlite-pane-verbose*
Verbose ~
    curl's `--verbose` trace: connection setup, the TLS handshake and ALPN
    negotiation, every header actually sent and received. When a request
    behaves differently here than in a shell, the answer is usually here.

                                                        *curlite-pane-script*
Script ~
    Everything your scripts logged with `client.log`, and every assertion —
    `# @assert` expressions and `client.test` blocks alike — with a
    `3 passed, 1 failed` tally and the detail of each failure.

Drop any pane you never look at from `ui.panes`; it disappears from the
winbar and from the pane cycle.

------------------------------------------------------------------------------
WHERE THE WINDOW OPENS                                       *curlite-display*

`ui.display` takes one of:

    "right"     a vertical split on the right     (the default)
    "left"      a vertical split on the left
    "below"     a horizontal split below
    "above"     a horizontal split above
    "float"     a centred floating window
    "tab"       a new tab page

`"vertical"` and `"horizontal"` are accepted as aliases for `right` and
`below`.

For a vertical split, `ui.width` controls the width; for a horizontal one,
`ui.height` controls the height. A value between 0 and 1 is a fraction of the
editor (`0.5` is 50%), a value of 1 or more is an absolute cell count, and 0
leaves the size to Neovim. A size changed by hand is restored as a fraction,
so toggling or resizing the terminal does not distort the layout.

For `display = "float"`, `ui.float.width` and `ui.float.height` are fractions
of the editor (`0.8` is 80%) and `ui.float.border` is any value that
|nvim_open_win| accepts — `"rounded"`, `"single"`, `"double"`, `"solid"`,
`"none"`, or a table of characters. The same border is used for the
|curlite-inspect| popup.

`ui.focus` decides where the cursor lands. The default `false` leaves you in
the request buffer so you can fire the next request immediately; `true` jumps
into the response. Either way `:Curlite open` focuses it, and `gd` in the
response window jumps back to the request that produced it.

The window sets `winfixbuf`, so a stray `:bnext`, a quickfix jump or a plugin
cannot replace the response with something else. curlite lifts that flag only
for its own pane switching.

Other display options: `ui.wrap` (off), `ui.number` (off), `ui.cursorline`
(off), `ui.winbar` (on — set false to lose the pane tabs and the status line),
and `ui.inline_status` (on — the ` 200 OK` virtual text at the end of the
request line, cleared as soon as you edit the buffer, because a stale one is
worse than none).

                                                           *curlite-inline*
What that inline text contains is `ui.inline`. Only the status is on by
default: the winbar one split away already carries the timing, the size and
the assertion tally, and repeating them at the cursor is noise rather than
information. >lua

    require("curlite").setup({
      ui = {
        inline = {
          icon = true, status = true,   -- ` 200 OK`
          time = false,                 -- `· 143ms`
          size = false,                 -- `· 2.7KB`
          tests = false,                -- `· 2/2`
        },
      },
    })
<
A failing assertion recolours the status whether or not the tally is shown, so
turning it off never hides a failure. With every part off nothing is drawn at
all, which is the same as `inline_status = false`.

                                                            *curlite-flash*
`ui.flash` briefly highlights the request in the buffer as it is sent, so a
fired request registers at the cursor and not only in the response window. >lua

    require("curlite").setup({
      ui = {
        flash = true,
        flash_timeout = 1500,   -- ms; 0 holds it until the response lands
        flash_scope = "request",
      },
    })
<
`flash_scope` is `"request"` — the complete section from its `###` header
through its final body or script line — or `"line"` for the request line alone.

It is drawn with `CurliteFlash`, linked to `Visual` by default.

------------------------------------------------------------------------------
MAPPINGS IN THE WINDOW                                *curlite-result-keymaps*

All configurable through `result_keymaps`; set one to `false` to drop it, or
`result_keymaps = false` to bind everything yourself.

    q           close the window
    B H A       body / headers / all
    S T O       stats / trace (verbose) / script output
    <C-l>       next pane
    <C-h>       previous pane
    1 .. 6      jump straight to a pane, in `ui.panes` order
    ]           newer response from the history
    [           older response
    gd          jump to the request that produced this response
    Y           yank the body (respects the register you prefix)
    gs          save the body to a file
    gq          jq filter over a JSON body, in place
    <Esc>       clear the filter
    gi          open the body in its own tab, as a scratch buffer
    R           re-send the request that produced this response
    <leader>Ro  hide the window (the same key that opens it from the request)

`/` is left alone: it searches the response like it does in any other buffer.

                                                            *curlite-filter*
In a JSON Body pane, `gq` runs your expression through `jq` over the raw body
and shows the result. In every other pane, and for a non-JSON body, the key
falls through to whatever it normally does. The jq result is a view, not a
change — `[`, `]` and a new request all clear it, and `<Esc>` restores the
whole body. Anything jq accepts works:

    .items | length
    .data[] | select(.active)
    {name, id}
    [.items[].id]

It needs `jq` on PATH; without it the key reports that and does nothing.

                                                           *curlite-scratch*
`gi` takes the other route: it opens a copy of the body in a new tab, as an
ordinary modifiable buffer with the body's filetype. From there the whole of
Vim applies, `jq` included and on your terms: >

    :%!jq '.items | map(.id)'
    :%!jq -r '.data[].email'
    :'<,'>!jq .
    :g/"active": false/d
<
It is a copy. Nothing is written back to the response, the response window
stays where it is, and the buffer is `nofile`, so `:w some.json` is how it
leaves. `q` wipes it, filtered or not -- no prompt about unsaved changes. Press
`gi` again for a fresh copy.

`:Curlite body` does the same thing from anywhere, including from the request
buffer with the response window closed.

                                                           *curlite-history*
`[` and `]` walk back through the last `history.size` responses (50 by
default; `0` is unlimited). The winbar shows `[2/7]` while you are not on the
newest. A skipped request never enters the history, because there is nothing
to look at.

------------------------------------------------------------------------------
FILETYPES                                            *curlite-config-filetype*

`filetypes` ~
    The filetypes curlite attaches to. Buffer-local keymaps and `on_attach`
    fire for each. Default `{ "http" }`.

`filetype.register` ~
    Whether curlite calls |vim.filetype.add| at all. Neovim already detects
    `.http`; this adds the rest. Set `false` to own it yourself.

`filetype.extensions` ~
    Extra extensions mapped onto `http`. Default `{ "rest" }`.

`filetype.patterns` ~
    Lua patterns mapped onto `http`, in the form |vim.filetype.add| expects.
    The default `[".*%.http%..*"]` catches `api.http.dev`, `api.http.local`
    and friends.

`on_attach` ~
    `function(bufnr)`, run once per `.http` buffer after the built-in keymaps
    are applied. The place for your own buffer-local binds: >lua

        on_attach = function(buf)
          local c, o = require("curlite"), { buffer = buf, silent = true }
          vim.keymap.set("n", "<CR>", c.run_at_cursor, o)
          vim.keymap.set("n", "<leader><CR>", c.run_all, o)
        end
<
------------------------------------------------------------------------------
CURL                                                     *curlite-config-curl*

`curl.path` ~
    Path to the binary. `"curl"` looks it up on PATH.

`curl.args` ~
    Flags prepended to every request. `--location` follows redirects the way
    every other REST client does by default; `--no-buffer` keeps a streaming
    response arriving promptly. Replace the table to drop either.

`curl.timeout` ~
    Milliseconds before a request is abandoned, `0` to disable. A per-request
    `# @timeout` overrides it. curlite also arms a backstop two seconds later
    in case curl wedges before its own `--max-time` applies.

`curl.verify_ssl` ~
    `false` adds `--insecure` to everything. Prefer `# @insecure` on the one
    request that needs it.

`curl.cookie_jar` ~
    Path to a shared cookie jar, or `false` to disable cookies entirely. The
    jar is why a login request's session carries into the next request with
    no work on your part — and why `# @no-cookie-jar` exists for when you
    want a request to be genuinely unauthenticated.

------------------------------------------------------------------------------
REQUESTS                                              *curlite-config-request*

`request.variables_scope` ~
    `"request"` (default) — a document variable is visible to the requests
    below it, so redefining one mid-file does what it looks like.
    `"document"` — every request sees the file's final value for every
    variable, regardless of order. This is kulala's behaviour.

`request.default_headers` ~
    Merged into every request, but only where the request did not set the
    header itself (matched case-insensitively). Set to `{}` to send nothing
    you did not write.

`request.infer_content_type` ~
    When a body parses as JSON and no `Content-Type` was given, send
    `application/json`. `false` leaves the header off.

`request.substitute_in_response` ~
    Expand `{{...}}` in the response body too. Off, because a response that
    happens to contain braces should come back untouched.

------------------------------------------------------------------------------
UI                                                         *curlite-config-ui*

`ui.display`, `ui.width`, `ui.height`, `ui.float`, `ui.focus`, `ui.wrap`,
`ui.number`, `ui.winbar`, `ui.inline_status`, `ui.inline`, `ui.flash`,
`ui.flash_timeout`, `ui.flash_scope`, `ui.panes`, `ui.default_pane`
are all covered in |curlite-response-window| and |curlite-display|.

`ui.picker` ~
    Geometry of the environment picker: `width` and `height` as fractions of
    the editor (or absolute counts above 1), `list_width` as the fraction of
    that width the list of names takes, `border`, and `preview` -- `false`
    drops the variable pane and leaves a plain list of names. Defaults `0.8`,
    `0.7`, `0.3`, `"rounded"`, `true`. It is large on purpose; see
    |curlite-env-selecting|.

`ui.picker.backend` ~
    Which front end opens it. `"auto"` (default) uses telescope.nvim when it
    is installed and curlite's own window otherwise; `"telescope"` asks for
    telescope and says so if it is missing; `"builtin"` never reaches for it.
    The geometry above applies to both. See |curlite-env-telescope|.

`ui.picker.telescope` ~
    Passed to telescope's picker and merged over curlite's defaults: a
    `layout_strategy`, a `layout_config`, a theme's fields, anything
    `telescope.pickers.new` accepts. Note that curlite sets
    `preview_cutoff = 0`, because telescope would otherwise hide the variables
    below 120 columns and the variables are what you are choosing by.

`ui.icons` ~
    Single characters shown beside a status, in the winbar and in the inline
    virtual text. Set any to `""` to drop it. Keys: `success`, `error`,
    `running`, `redirect`. They need a Nerd Font; plain alternatives: >lua

        icons = { success = "✓", error = "✗", running = "…", redirect = "→" }
<
`ui.cursorline` ~
    Highlight the line the cursor is on in the response window. Default
    `false`. The response is something you read and copy out of, and a bar
    tracking the cursor across it reads as noise rather than as position.
    Set it to `true` for the usual 'cursorline' behaviour.

`ui.highlights` ~
    What the six status highlight groups link to. See |curlite-highlights|.

------------------------------------------------------------------------------
RESPONSES                                            *curlite-config-response*

`response.format` ~
    Pretty-print bodies. `false` shows every body exactly as it arrived.

`response.indent` ~
    Spaces per level for the JSON and XML formatters, and for the `gq`
    filter.

`response.filetypes` ~
    Content-Type substring → buffer filetype for the Body pane.
    Add your own: >lua

        response = { filetypes = { toml = "toml", csv = "csv" } }
<
    Matching walks a fixed order — json, html, xml, javascript, css, yaml,
    csv, text — so `application/xhtml+xml`, which contains both "html" and
    "xml", always resolves the same way. Keys you add that are not in that
    list are tried afterwards, longest first.

`response.max_format_size` ~
    Bodies larger than this (bytes) are shown raw, unformatted and without a
    filetype, so a 40MB payload does not lock the editor. `0` removes the
    limit.

`response.show_request` ~
    Include the request half of the `all` pane.

------------------------------------------------------------------------------
FORMATTING                                             *curlite-config-format*

`:Curlite format` rewrites the buffer you are editing. It is pure Lua: there is
no binary to install and no language server to configure.

It normalises what curlite already understands and leaves everything else
byte-for-byte:

    - `###` separators collapse to one `###` and a single space
    - `@name=value` becomes `@name = value`
    - the method is upper-cased and spacing around the URL is made single
    - `Header :  value` becomes `Header: value`
    - a continued query parameter is indented two spaces under its URL
    - a JSON body is re-indented

Prose comments, non-JSON bodies and script blocks are never touched. The
formatter is idempotent: running it on an already-formatted document is a
no-op, so it is safe on `BufWritePre`.

`format.bodies` ~
    Re-indent JSON request bodies. Default `true`. A `{{template}}` inside a
    body survives, including where it stands in for a number and the body is
    therefore not valid JSON on its own. A body that does not parse is left
    alone, so a half-typed payload is never mangled.

    This also governs the resolved-request previews -- |curlite-hover|,
    |curlite-inspect| and the `[confirm]` popup -- which indent a JSON body for
    display without touching the buffer.

`format.indent` ~
    Spaces per indent level for a JSON body, both in the buffer and in a
    preview. Default `2`.

`format.on_save` ~
    Format automatically just before the buffer is written. Default `false`. >lua

        require("curlite").setup({ format = { on_save = true } })
<
------------------------------------------------------------------------------
HIGHLIGHTING                                        *curlite-config-highlight*

Colouring of the `.http` buffer you edit. The response window is separate; see
|curlite-highlights|.

`highlight.enable` ~
    Draw curlite's extmarks at all. Default `true`. Setting it to `false`
    clears what is drawn and leaves the buffer to Treesitter or the bundled
    syntax file alone.

`highlight.methods` ~
    Per-method colours, as `dark` and `light` tables keyed by method name. See
    |curlite-method-highlights|.

`highlight.method_style` ~
    Attributes applied to every method group alongside its colour. Default
    `{ bold = true, italic = false }`.

`highlight.url` ~
    The request URL: `{ dark = "#...", light = "#...", underline = true }`.

`highlight.line_bar` ~
    A full-width background bar behind structural lines. Default `"none"`.

        "none"       no bar anywhere
        "separator"  behind `###` section lines only
        "all"        behind `###` lines and header lines

    The bar is drawn with `highlight.line_bar_group`, `CursorLine` by default.
    It is off because a bar on every header line bands the whole file, which
    reads as a rendering fault rather than as structure: >lua

        require("curlite").setup({
          highlight = { line_bar = "separator" },
        })
<
------------------------------------------------------------------------------
ENVIRONMENTS                                              *curlite-config-env*

`env.files` ~
    Filenames searched for in the `.http` file's directory and every
    directory above it. Later entries are merged over earlier ones, which is
    what makes `http-client.private.env.json` an overlay on the public file.

`env.dotenv` ~
    Filename read for `{{$dotenv NAME}}`, or `false` to disable.

`env.default` ~
    Environment to start with. `nil` -- the default -- means *none*: curlite
    never guesses one and never carries the last choice into a new buffer.
    Name one here only if you want it active without being asked.

`env.require_selection` ~
    With environments defined and none selected, a send opens the picker
    instead of going out; the request follows once you have chosen. `false`
    lets requests run against the shared variables alone. See
    |curlite-env-selecting|.

`env.shared_key` ~
    The key whose contents are merged under every environment, or a list of
    them with earlier names winning. `{ "$curliteshared", "$shared" }`.
    JetBrains' `$shared` is always read, whatever you set here.

`env.headers_key` ~
    The key inside an environment object that holds default headers rather
    than variables, or a list of them with earlier names winning.
    `{ "$default_headers", "$defaultHeaders" }`. See |curlite-env-headers|.

------------------------------------------------------------------------------
SCRIPTS                                               *curlite-config-scripts*

`scripts.enable` ~
    `false` ignores every `{% %}` block, every external script and every
    `# @assert`.

`scripts.sandbox` ~
    Scripts get a restricted `_ENV` with no `io`, `os.execute`, `debug`,
    `jit`, `require` or the loaders. Set `false` when you script against your
    own modules — you then own what they can reach.

`scripts.timeout` ~
    Wall-clock budget in milliseconds for a single script block or `# @assert`
    expression, `0` to disable. Scripts run on the main loop, so this is what
    stops `while true do end` from hanging the editor: a count hook checks the
    clock and raises. Enforcing it requires running the script interpreted, so
    it is off the JIT for those few milliseconds.

------------------------------------------------------------------------------
NOTIFICATIONS                                        *curlite-notifications*

Every message curlite shows is tagged with an event name, so a message you
find noisy is turned off by name rather than by turning the plugin quiet: >lua

    notify = {
      events = {
        env_selected = false,        -- stop announcing the environment
        request_done = "warn",       -- 4xx/5xx only; 200s are silent
      },
    }
<
`:Curlite events` prints the full list with each event's default level and
whether your current configuration lets it through.

                                                          *curlite-notify-events*
THE EVENTS ~

Request lifecycle:
    `request_sent`      a request is going out                 (off by default)
    `request_done`      a response landed; WARN for 4xx/5xx
    `request_skipped`   a pre-request script skipped it        (off by default)
    `request_aborted`   a script aborted a `send_all` run
    `request_error`     the request could not be built or sent
    `run_summary`       the tally after `send_all` / `:CurliteRun`
    `cancelled`         in-flight requests were cancelled

Environments:
    `env_selected`      "environment → staging"
    `env_required`      a send was held back until you pick one
    `env_missing`       no environment file was found

The document:
    `no_request`        no request under the cursor, or in the file
    `duplicate_names`   two requests in a file share a name
    `parse_error`       a file or a curl command would not parse

Resolving a request:
    `import_error`      `# @import` could not read a file
    `chain_error`       `# @run` names a request that does not exist
    `variable_error`    `{{$exec ...}}` and friends failed
    `script_error`      a pre/post-request script raised

Clipboard and files:
    `yank`              something was copied to a register
    `save`              a response body was written to disk
    `write_error`       a `>>` redirect could not be written

The response window:
    `no_response`       `toggle` with nothing to show           (off by default)
    `cleared`           session state was cleared               (off by default)

Anything curlite has not given a name of its own is `info`, `warn` or `error`.

                                                        *curlite-notify-options*
THE OPTIONS ~

`notify.enabled` ~
    The master switch. `false` and nothing is ever notified — errors included,
    which is usually not what you want. Silence events by name instead.

`notify.level` ~
    The severity floor for ordinary events: `"error"`, `"warn"` (default),
    `"info"`, `"debug"`, `"trace"` or `"off"`, or a |vim.log.levels| number.

    Some events ignore it. Those are the ones that answer a question you just
    asked ("did the yank land?") or report that something you asked for did
    not happen; hiding those behind a severity threshold makes the plugin look
    broken rather than quiet, so they are only turned off by naming them in
    `events`. `:Curlite events` marks them.

`notify.events` ~
    Per-event overrides, keyed by the names above. Each value may be:

        `false`             never notify for this event
        `true`              always notify, ignoring `level`
        `"warn"`, `3`, ...    a threshold just for this event

    A name that is not an event does nothing, silently — `:checkhealth
    curlite` reports the typo.

`notify.filter` ~
    `function(ev) -> boolean|nil`, run after everything above and given the
    last word. `ev` is `{ event, level, shown, msg, data }`, where `data`
    carries whatever the call site knew — the result, the status, the
    environment name. Return a boolean to override the decision, `nil` to keep
    it: >lua

    notify = {
      filter = function(ev)
        -- announce slow requests, however they ended
        if ev.event == "request_done" and ev.data.result then
          return ev.data.result.response.duration_ms > 1000
        end
      end,
    }
<
`notify.backend` ~
    Route messages somewhere other than |vim.notify|: a notifier plugin, a
    statusline, a log file. `function(msg, level, opts)`, where `opts` is
    `{ title, event, data }`. `nil` uses `vim.notify`. >lua

    notify = {
      backend = function(msg, level, opts)
        require("fidget").notify(msg, level, { annote = opts.event })
      end,
    }
<
`notify.title` ~
    The `title` passed to `vim.notify`, which most notifier plugins show.
    Default `"curlite"`.

                                                        *curlite-notify-legacy*
The older spelling still works and means what it always did: >lua

    notify = "errors"   -- the default: failures only
    notify = "all"      -- also a line as each request starts and lands
    notify = "none"     -- silent
<

------------------------------------------------------------------------------
EVERYTHING ELSE                                          *curlite-config-misc*

`history.size` ~
    Responses kept for `[` and `]`. `0` is unlimited.

`history.max_bytes` ~
    A byte ceiling on the ring, because a count alone is not a bound: fifty
    250KB responses is a lot to hold for a feature you use occasionally.
    Oldest entries are dropped until every retained body, header dump and
    verbose trace fits. The newest response is always kept, however large.
    `0` disables the check. Default 16MB.

    Derived data is not kept either: the decoded body of every response but
    the newest is dropped, since a chained `{{NAME.response.body.$.x}}` falls
    back to decoding the text it still has.

`notify` ~
    Which `vim.notify` messages get through, and where they go. See
    |curlite-notifications|.

`debug` ~
    Write every command line to `stdpath("log")/curlite.log`. `:Curlite log`
    opens it.

`keymaps`, `result_keymaps` ~
    See |curlite-mappings| and |curlite-result-keymaps|. Set one entry to
    `false` to drop it, or the whole table to `false` to bind everything
    yourself.

16. COMPLETION                                            *curlite-completion*

Completion needs no plugin. Every `.http` buffer gets an 'omnifunc', so
|i_CTRL-X_CTRL-O| completes, and after `{{` the menu opens by itself as you
type. Sources for blink.cmp and nvim-cmp are included and offer exactly the
same items.

Inside `{{ }}` you are offered:

    - the document's `@variables`, with their values
    - the shared block's variables, marked `$curliteshared`
    - the selected environment's variables, marked with its name
    - nested paths, so `{{auth.clientId}}` completes as `auth.clientId`
    - script globals and prompt answers
    - the dynamic `{{$...}}` functions, with what each returns
    - `NAME.response.body.$.`, `NAME.response.status` and
      `NAME.response.headers.` for every named request in the file

Only what would actually resolve is offered: with no environment selected you
get the shared variables and nothing else, and an environment you have not
selected never appears. A name defined in two places is described by the value
that would win at send time.

                                                        *curlite-completion-braces*
A variable completes to the whole `{{name}}`. The menu lists bare names, but
accepting one writes the braces with it, replacing whatever `{{...}}` the
cursor is in:

    GET {{ho            ->  GET {{host}}
    GET {{auth.cl       ->  GET {{auth.client_id}}
    GET {{$uu           ->  GET {{$uuid}}
    GET {{}}            ->  GET {{host}}        (an autopaired pair is reused)
    GET {{host}}        ->  GET {{token}}       (re-completing replaces it all)

Each item names the exact range it replaces, rather than leaving the engine to
work it out from its own keyword pattern -- blink's stops at `$` and `.`, so
its idea of the word in `{{auth.cl` is `cl`, and accepting would otherwise
have written `{{auth.auth.client_id`.

A path that is still being written -- `LOGIN.response.body.$.` -- leaves the
cursor between the braces so you can go on typing it. A finished name leaves
it after them.

At the start of a line it offers methods and header names; after
`Content-Type:` and friends it offers plausible values; after `# @` it offers
the metadata keys with a description of each.

blink.cmp: >lua

    require("blink.cmp").setup({
      sources = {
        providers = {
          curlite = { module = "curlite.blink", name = "curlite" },
        },
        per_filetype = { http = { "curlite", "path", "buffer" } },
      },
    })
<
nvim-cmp — the source registers itself when cmp is loaded, so it only needs
naming: >lua

    require("cmp").setup.filetype("http", {
      sources = { { name = "curlite" }, { name = "buffer" } },
    })
<
                                                       *curlite-config-completion*
Options: >lua

    completion = {
      enable = true,        -- set `omnifunc` on http buffers
      auto_trigger = true,  -- open the menu after `{{`, with no engine loaded
      cmp = true,           -- register the nvim-cmp source when cmp is there
    }
<
`auto_trigger` stays out of the way when blink.cmp or nvim-cmp is loaded —
they do their own triggering. To pop the menu open it needs 'completeopt' to
carry `noselect` or `noinsert`; where Neovim allows a buffer-local
'completeopt' curlite sets one for `.http` buffers only, and where it does not
(Neovim 0.10) it leaves yours alone and does nothing unless it already says so.

                                                    *curlite-method-highlights*
Methods get one group each, with a concrete colour rather than a link: >

19. COMING FROM KULALA                                        *curlite-kulala*

The file format is the same, so your existing `.http` files and
`http-client.env.json` work unchanged. What differs:

    scripts             Lua, not JavaScript. `client.global.set`,
                        `request.skip`, `request.abort` and `client.test` keep
                        their names; the bodies are Lua.
                        (|curlite-scripts|)
    no backend          no companion binary and no tree-sitter CLI. curl is
                        the only requirement.
    protocols           HTTP and GraphQL. No gRPC, WebSocket or streaming.
    OAuth2              no built-in flow; chain a token request instead
                        (|curlite-auth|)
    OpenAPI explorer    not included
    filtering           a jq expression over the body (`gq` in the response
                        window), rather than kulala's filter syntax
    environments        nothing is selected until you pick one. Opening a file
                        starts with none, and the first send opens the picker
                        rather than reusing an earlier choice
                        (|curlite-env-selecting|)

Everything else — environments, the shared block, dynamic variables, request
chaining, prompts, assertions, the `>>` redirect, `< file` bodies, multipart,
the scratchpad — behaves the same way.

20. TROUBLESHOOTING                                  *curlite-troubleshooting*

`:checkhealth curlite` first.

A request behaves differently here than in a shell ~
    `<leader>Ri` shows the resolved request and the exact curl command line it
    becomes. Paste that into a shell and compare. `<leader>Rc` yanks it; for a
    named request, its `### NAME` is kept as a shell comment above the command.

The Verbose pane ~
    curl's `--verbose` trace, including the TLS handshake and every header
    actually sent. This is usually where the answer is.

`unresolved variable: x` ~
    The request was refused rather than sent with a literal `{{x}}`. Either
    the name is misspelled, no environment is selected (`<leader>Re`), or it
    refers to a request that hasn't run yet — in which case `# @run` will run
    it for you.

A form body comes back as a 400 ~
    Check the Stats pane's `Content type`. `application/x-www-form-urlencoded`
    bodies have their newlines stripped; anything else is sent verbatim,
    newlines included.

TLS certificate errors ~
    `# @insecure` on the request, or `curl.verify_ssl = false` globally.

A debug log ~
    `debug = true` writes every command line to
    `stdpath("log")/curlite.log`; `:Curlite log` opens it.

vim:tw=78:ts=8:et:ft=help:norl:
